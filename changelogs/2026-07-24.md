# 2026-07-24

## 新增:内嵌浏览器支持 iPad UA 切换

### 背景
很多视频站点桌面版的 player 套了好几层壳(video.js / shaka / 自研 DRM
包装),JSExtractor 不一定抓得到 m3u8 源,而且部分站点对桌面 UA 直接 403
或返回不一样的页面。换成 iPad Safari UA 后,服务端倾向于返回平板版
HTML5 player,通常更直白、m3u8 source 更容易在 video element / hls.js
实例里露出来。

### 改动
- `BrowserViewModel.swift`:
  - 新增 `static let iPadUserAgent: String` —— 标准 iPad Safari 17 UA
    (`Mozilla/5.0 (iPad; CPU OS 17_0 like Mac OS X) AppleWebKit/605.1.15
    (KHTML, like Gecko) Version/17.0 Mobile/15E148 Safari/604.1`)
  - 新增 `@Published var useIPadUA: Bool`,UserDefaults key
    `m3u8dl.useIPadUA` 持久化,默认 `false`(保持现有桌面行为)
  - 新增 `func setUseIPadUA(_:)` —— flip flag + 同步更新现有
    `WKWebView.customUserAgent` + `wv.reload()` 当前页。`didSet` 写
    UserDefaults,setter 里 `guard enabled != useIPadUA else { return }`
    避免无效重复 reload
- `WebBrowserView.makeNSView` 在创建 WKWebView 时读
  `vm.useIPadUA`,设 `wv.customUserAgent = iPadUA : nil`(nil 走
  默认 macOS Safari UA)
- `BrowserView` 导航栏右侧(loading indicator 之后)加切换按钮:
  - iPad 模式:`Image(systemName: "ipad")`,`foregroundStyle = .accentColor`
  - 桌面模式:`Image(systemName: "desktopcomputer")`,`foregroundStyle = .secondary`
  - tooltip:`"当前:iPad UA(点击切回桌面)"` / `"当前:桌面 UA(点击切到 iPad)"`
  - 点击 → `vm.setUseIPadUA(!vm.useIPadUA)`,自动 reload 当前页

### 影响范围
- iPadOS 13+ 在真机上会"伪装 Mac"避免被推桌面版,但 macOS 上 WKWebView
  不会做这个伪装 —— 我们手动设什么 UA,服务端就看到什么。普通的
  `iPad; CPU OS 17_0 like Mac OS X` 字串就够触发 iPad 路径
- HLS 探针 / N_m3u8DL-RE 都不受此影响 —— 只动内嵌浏览器请求的 UA
- 不会动 `HTMLDiscoverer.swift` 里给直连 m3u8 URL 设的默认 Chrome UA
  (那是给"从 HTMLDiscoverer 抓到的链接"用,跟浏览器渲染无关)
- 没动 PlayerViewModel / DownloaderViewModel / ProcessRunner

### 副作用 / 已知保留
- 切完等页面 reload 完成才看到效果(几百 ms),不是即时
- 不影响 WKWebView 已经在内存里持有的资源(cached 资源可能还是用老 UA
  抓的);如果发现切完页面没区别,先 ⌘R 或点 Stop 再访问一次清缓存
- 状态只持久化 `useIPadUA` 一个 bool;没存"每个站点单独记忆 UA"
  这种高级功能,个人项目用不上
- 没在 Settings 场景里再加一个开关 —— 导航栏已经够顺手,场景里
  重复一遍反而干扰

### 调整:iPad UA 改为默认
用户偏好 iPad UA 作为默认(理由同上,iPad 布局对抓 m3u8 更友好)。
只影响"还没手动存过值"的新装机用户 —— 已经在导航栏里手动选过桌面
UA 的人,`m3u8dl.useIPadUA` key 存的是 `false`,启动时读 UserDefaults
的逻辑保留他们的选择;没存过 key 的人(也就是这条 commit 之前
的所有用户,包括这次新装的)启动时拿到 iPad UA。

实现:`useIPadUA` 的初始化闭包在 `defaults.object(forKey: ...) == nil`
时返回 `true` 而不是 `false`;doc comment 同步更新说明。

## 新增:内嵌浏览器登录态持久化 + 清除按钮

### 背景
WKWebView 默认使用 `nonPersistent()` data store(从 iOS 13 / macOS 隐
私策略起),cookies / localStorage / IndexedDB / cache 都不落盘,关掉
App 登录态就丢。这对"我打开网站 → 登录 → 拿 m3u8"的流程很别扭:每
次启动都要重新登录。

### 改动
- `WebBrowserView.makeNSView`:
  - `WKWebViewConfiguration.websiteDataStore = .default()`(显式覆盖
    默认的 non-persistent)
  - `.default()` 是 singleton,所有 WKWebView 实例共享同一个 cookie
    jar;数据写到 `~/Library/WebKit/local.m3u8downloader/`,与 Safari
    数据隔离
  - 注释里写明原因,免得后人以为是 .nonPersistent() 出 bug
- `BrowserViewModel.clearAllWebsiteData()`:
  - `WKWebsiteDataStore.removeData(ofTypes: allWebsiteDataTypes(),
    modifiedSince: epoch)` 异步清空所有持久化数据
  - 完成后 `webView?.reload()`,用户立刻看到已登出 / 干净状态
- `BrowserView` 导航栏右侧(iPad 切换按钮之后)加 `trash` 图标按钮:
  - 点击弹 `NSAlert` 二次确认("会登出所有已登录网站、清除
    localStorage、IndexedDB 和缓存..."),确认后调
    `vm.clearAllWebsiteData()`
  - 误点会登出所有站,所以强制走确认

### 影响范围
- 旧用户(以及现在还没存过 key 的用户)首次启动会建一个新的
  default data store,新登录的站会持久化
- 不影响内嵌浏览器抓 m3u8 的主链路 —— JSExtractor 跟
  websiteDataStore 没关系
- 不影响 HTMLDiscoverer.swift 里的直连 m3u8 URL 抓取(那条路径走
  URLSession,跟 WKWebView 无关)
- 不影响 PlayerViewModel / DownloaderViewModel / ProcessRunner

### 副作用 / 已知保留
- `~/Library/WebKit/local.m3u8downloader/` 现在会有真实数据
  (cookies / cache 可能几 MB),不打算清理,个人项目用
- 跨 App 隔离:这跟 Safari / 其他 app 的 cookie 不共享,只能在这
  个 m3u8 下载器里用 —— 这是设计如此,不是 bug
- 没做"只清 cookies / 只清缓存"的细粒度选项,一个 trash 按钮统一
  干完。要更细以后再加
- `removeData` 走的是 completion handler,UI 不会卡;但完成时机
  WebKit 不保证,可能 reload 触发时 data store 还有陈旧条目,
  实测没复现,先这样

## 调整:UA 切换 + 清除数据按钮合并到右侧"浏览器请求"面板

### 背景
之前 iPad UA 切换和 clear 数据两个按钮都放在左侧 nav bar (URL 栏
右侧、loading indicator 之后)。nav bar 已经塞了 back/forward/reload/
stop 4 个按钮 + URL field + loading,再加两个就有点挤。这两个按钮
语义上都是"对 server 的请求配置",跟右侧"HTTP 请求头"是一类,放回
nav bar 既挤又不内聚。

### 改动
- `BrowserViewModel`:
  - 把 webview 同步(customUserAgent + reload)从 `setUseIPadUA()`
  方法挪到 `useIPadUA.didSet`,这样 SwiftUI 的 `Picker` 直接绑
  `$vm.useIPadUA` 就能自动触发刷新
  - 删除 `setUseIPadUA()` 方法(didSet 接管了)
  - `clearAllWebsiteData()` 不动
- `BrowserView`:
  - 移除左侧 nav bar 的 iPad toggle button 和 trash button
  - 在右侧 `inputControlsPanel` 里、`"直接粘贴 m3u8 链接"` DisclosureGroup
  和 `"HTTP 请求头"` DisclosureGroup 之间新增一个常驻
  `"浏览器请求"` 小面板:
    - UA 模式:`Picker` 绑 `$vm.useIPadUA`,`segmented` 样式,标签
    "桌面" / "iPad",固定宽 140pt
    - 清除数据:trash 图标 + 文字 label,NSAlert 二次确认后调
    `vm.clearAllWebsiteData()`
    - 整块用跟"HTTP 请求头"列表相同的 `.quaternary.opacity(0.25)`
    圆角灰底,视觉对位

### 影响范围
- Picker 比单按钮更直白,点哪个就是哪个,不需要看 tooltip
- 切换 UA 仍然是 didSet 触发 reload,行为跟之前一致
- 左侧 nav bar 现在只剩 back/forward/reload/stop + URL + loading
  indicator,清爽了
- 没动 PlayerViewModel / DownloaderViewModel / ProcessRunner /
  WebBrowserView / WebView 持久化逻辑(那部分昨天 15:07 已经写过)
- showHeaders 默认 `false`,所以"浏览器请求"小面板常驻在视野里,
  iPad UA 切换永远不需要展开任何 DisclosureGroup 就能点到 —— UX
  上比之前 nav bar 还顺手

## 调整:右上"浏览器设置" DisclosureGroup(默认折叠),内含三子区

### 背景
上一版把 iPad UA 切换和清除数据合并到右侧"浏览器请求"小面板
(常驻),虽然语义对位了,但默认就一直占着右侧一整块,初始视觉
有点挤 —— 用户更多时候是来探测 m3u8,不是来调浏览器配置。改成
包成一个 "浏览器设置" 大 DisclosureGroup,默认折叠,展开后里面
是三个子区(UA 头 / 清理缓存 / HTTP 请求头(可选))。需要时点
开,不需要时收起,空间更灵活。

### 改动
- `BrowserView`:
  - `@State showHeaders: Bool` 重命名为 `showBrowserSettings: Bool`
    (默认 false,折叠)
  - 删除上一版"浏览器请求"小面板(被吸收进新的 DisclosureGroup)
  - 原 "HTTP 请求头(可选)" DisclosureGroup 改名为 "浏览器设置",
    icon 从 `list.bullet.rectangle` 换成 `gearshape`(语义更通用)
  - 展开内容按用户要求拆成三块,每块一个 `sectionTitle` 小 label
    (复用 `private func sectionTitle`) + 自己的灰底圆角块:
    - **UA 头**:segmented Picker `桌面` / `iPad`,绑 `$vm.useIPadUA`,
    宽 160pt(比上一版 140pt 略宽,免得"桌面"两字裁切)
    - **清理缓存**:左边一句 caption 说明"会清什么",右边 `清除数据`
    trash 按钮(NSAlert 二次确认后调 `clearAllWebsiteData()`)
    - **HTTP 请求头(可选)**:沿用之前的 TextField + 添加按钮 + 列表
    UI,完全不动逻辑

### 影响范围
- `BrowserViewModel` 没动 —— `useIPadUA` didSet 还是自动 reload
  当前页,`clearAllWebsiteData()` 行为不变,`headers` 增删逻辑不变
- `WebBrowserView` 没动 —— UA / 持久化都跟昨天一样
- 默认折叠意味着:用户首屏看到的是"直接粘贴 m3u8 链接"和链接卡片
  列表,清清爽爽,需要调浏览器配置再点开"浏览器设置"展开

### 副作用 / 已知保留
- 没把三个子区再各自做成 DisclosureGroup(三层折叠太深,UX
  反而乱);用 `sectionTitle` + 灰底块视觉分组足够清晰
- "浏览器设置"折叠时连 iPad UA 切换也跟着隐藏,需要点一下才能
  切 UA。这是用户明确要求的(他说"保持默认折叠状态"),不再像
  上一版那样常驻

## 修复:窗口缩小后 nav bar URL 框和"直接粘贴 m3u8 链接"被遮挡

### 背景
用户反馈窗口缩到一定宽度时:
- 左侧 nav bar 的 URL 输入框没了,只剩一个 back 按钮孤零零露着
  (forward / reload / stop 都被裁掉了)
- 右侧"直接粘贴 m3u8 链接" DisclosureGroup 整个不显示,直接从
  "浏览器设置"开始

### 根因
1. **URL 框被裁**:nav bar 的 HStack 里 4 个按钮 + TextField 没有
   任何优先级/最小宽度声明。SwiftUI 的 HStack 在子元素总自然宽度
   超过可用宽度时不会自动压缩,而是把 rightmost items 直接裁掉
   (不挤压、保留各按钮的原始宽度)。TextField 没有 `layoutPriority`
   也没有 `minWidth`,被第一个牺牲。
2. **"直接粘贴 m3u8 链接"消失**:`resultsPane` VStack 里
   `emptyState` 声明了 `.frame(maxWidth: .infinity, maxHeight:
   .infinity)`,在某些窗口尺寸下 SwiftUI 的布局协商把这个
   "贪婪"声明的优先级抬得过高,把 `inputControlsPanel` 整体压扁
   到 0 高度(或 0 visible 高度),DisclosureGroup 头被推出可视区。

### 修复
- `BrowserView` nav bar HStack:
  - TextField 加 `.layoutPriority(1)` —— 在 HStack 的宽度分配中
    优先拿到空间,按钮被挤压
  - TextField 加 `.frame(minWidth: 120)` —— 即便左栏被压到接近
    `minWidth: 460pt`,URL 框仍然可用
- `BrowserView.resultsPane`:
  - `inputControlsPanel` 加 `.layoutPriority(1)`,在 VStack 跟下面
    `emptyState` (maxHeight: .infinity) 抢空间时,优先保证面板的
    自然高度,不会被压扁
  - (第一版用的是 ScrollView{maxHeight:360} 把整个面板钉在 360pt,
    即使两个 DisclosureGroup 都折叠也留一大块空白,弃用)

### 影响范围
- 极端窄的窗口(左栏接近 460pt):URL 框可能仍被部分挤压,但永远
  至少 120pt 宽可见
- 正常宽度:行为不变,TextField 仍自动撑满剩余空间
- inputControlsPanel 现在有 360pt 高度上限,极端情况下
  (用户同时展开"直接粘贴 m3u8 链接"和"浏览器设置"里所有
  DisclosureGroup)面板内出现滚动条 —— 实际很少触发
- 没动 ViewModel / ProcessRunner / 其他文件

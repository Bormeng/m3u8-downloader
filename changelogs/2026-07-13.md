# 2026-07-13

## 调整:主窗口初始布局改为左 2/3 + 右 1/3

### 背景
主窗口用的是 SwiftUI 的 `HSplitView`,没设 divider 位置时 NSSplitView
默认就把分割线放在正中间。右侧面板(链接卡片 + 抓取输入 + 日志)其实
内容更密集 —— 链接卡片经常要滚,日志又要展示多行 —— 平分后右侧
视觉很挤、滚动条一出现就只剩一条缝;左侧浏览器/播放器反而经常空着
一大片。改成 2/3 : 1/3 后两边都舒服,链接卡片能显示更多内容。

### 改动
- `BrowserView`:
  - `inputPane`(左)idealWidth 540 → 720,作为 NSSplitView 的初始
    分割提示
  - `resultsPane`(右)新增 idealWidth = 360(之前没设)
  - 新增私有 `HSplitInitialDivider` NSViewRepresentable,挂在
    `inputPane.background()` 上,内部用 `HSplitDividerPinnerView`:
    - 走 `viewDidMoveToWindow` / `layout` 钩子,等 NSSplitView 拿到
      非零 width
    - 沿 superview 链向上找最近的 NSSplitView,调一次
      `setPosition(width × fraction, ofDividerAt: 0)`
    - `didApply` 一次性标记,避免 resize 时把用户拖动的位置拽回去
  - 整段注释里写了 *为什么* 不用 autosave / SwiftUI 为什么不暴露
    divider 位置 / 为什么不重复应用

### 影响范围
- 只动 `BrowserView.swift`,`PlayerView` / `ContentView` / ViewModel
  全部不动
- 窗口的 `minWidth: 760` 也没动 —— 现在两栏 `minWidth` 之和(920)还是
  大于 760,NSSplitView 会按需放宽,行为跟之前一样

### 副作用 / 已知保留
- 每次启动 divider 都钉在 2/3(用户拖动不持久化)。和原行为一致
  (之前也没设 autosave,只是默认 50/50 而已)
- 全屏状态下 NSSplitView 也会按 2/3 比例分,行为符合预期

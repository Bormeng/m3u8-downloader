# 2026-07-21

## 修复:N_m3u8DL-RE 在 GUI App 子进程模式下 SIGABRT(退出码 6)

### 背景
用户在终端里手动跑 N_m3u8DL-RE 一切正常,但在 App 里点"开始下载"每次都退
出码 6,产物为零(或只能落到 ffmpeg fallback)。

### 根因
N_m3u8DL-RE 用 Spectre.Console 渲染进度条。Spectre.Console 的
`LiveRenderable` / `ProgressRefreshThread` 在 `Console.IsOutputRedirected == true`
时(也就是我们 `Process()` 用 Pipe 接 stdout 时的状态)会进 race condition:

```
Unhandled exception. System.ArgumentException: Offset and length were out of bounds...
   at System.Collections.Generic.List`1.RemoveRange(Int32, Int32) + 0xa8
   at Spectre.Console.LiveRenderable.<Render>d__25.MoveNext() + 0x214
   at Spectre.Console.ProgressRefreshThread.Run() + 0xa8
```

本机复现:把 stdout/stderr 重定向到文件 + 模拟 GUI App 的 PATH(剥光 homebrew)
跑同样命令,得到 exit 134(SIGABRT)。Swift `Process.terminationStatus` 把
SIGABRT 报成 signal number 6,所以 App 日志里看到的是退出码 6。

这一条和 AGENTS.md 之前写的"N_m3u8DL-RE 在 macOS 上偶尔崩溃"是同一个 bug
家族 —— 之前提的 `List<T>.RemoveRange` 越界虽然对,但一直用 `--no-ansi-color`
等 hardening flag 只是把概率降低,没根治(进度条线程本身关不掉)。

### 修法:把 N_m3u8DL-RE 包在 PTY 里跑
加一层 `/usr/bin/script -q /dev/null`,让 .NET 进程以为 stdout 是真终端。
Spectre.Console 走 interactive 路径后不再 race。本机验证:

```
=== Terminal TTY ===         exit=0  →  ✓
=== Pipe(老行为)===          exit=134 →  ✗ Spectre race
=== Pipe + App env ===       exit=134 →  ✗ Spectre race
=== Pipe + script PTY ===    exit=0  →  ✓ 488MB mp4 落盘
```

### 改动
- `ProcessRunner.swift`:
  - `launch()` 新增参数 `pseudoterminal: Bool = false`
  - 当 true,内部 `executableURL = /usr/bin/script`,
    `arguments = ["-q", "/dev/null", <原 exe>, <原 args>...]`
  - stderr 重定向到 `/dev/null`(PTY 模型下 child 只有一条 stdout 流,
    再分一路只会 dup;N_m3u8DL-RE 在 PTY 下也确确实实只往 stdout 写东西)
- `DownloaderViewModel.swift`:
  - `buildArguments()` 移除硬化的 `--binary-merge`(PTY 跑成功后让 N_m3u8DL-RE
    自己走 ffmpeg mux,文件原汁原味);保留 `--disable-update-check --no-ansi-color
    --no-log`(去 GitHub 后台请求 / 去 ANSI 颜色 / 不在 saveDir 写 logs.txt)
  - `start()` / `startExternal()` 在 `launch(...)` 调用点上 `pseudoterminal: true`
  - `runFFmpegFallback()` 不开 PTY(ffmpeg 是 C 二进制,没这条 race)
- `AGENTS.md`:
  - 更新"N_m3u8DL-RE 在 macOS 上偶尔崩溃"段落,把"PTY 包装是主防线"写明,
    fallback 仅作为真正失败兜底
  - 新增一条产品决策:"下载链路默认走 N_m3u8DL-RE,因为快;ffmpeg 是兜底"

### 影响范围
- ffmpeg fallback 逻辑、`runFFmpegFallback`、`shouldFallback` 都没动 —— 兜底链路
  保留,只是不再当主防线
- 日志格式:`/usr/bin/script` 在第一行会有一个 `^D`(\x04)回声字符,会被
  `LogSeverity.classify` 当 `.comment` 显示为灰色文字。一次性污染,可接受

### 用户须知
跑一下 `bin/deploy_app.sh` 拿新版本。理论上现在 App 里点"下载"应该和终端里
直接跑一样,正常 N_m3u8DL-RE exit 0 + 自带 ffmpeg mux 出 mp4;只有在
N_m3u8DL-RE **真的**失败的极少数情况(被目标站点 403、URL 拿不到分片等)才
会看到 `[fallback]` 行 + ffmpeg 兜底。
